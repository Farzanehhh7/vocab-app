## ۰. اصلاح واقع‌بینانه Stack برای حالت تک‌نفره

سند معماری قبلی (v2.0) یک Backend جدا (NestJS) و یک Frontend جدا (Next.js) پیشنهاد داد — این برای یک **تیم چند نفره** تصمیم درستی است، اما برای **یک نفر**، یعنی دو ریپازیتوری، دو Deploy Pipeline، دو محیط env، و دو برابر overhead عملیاتی برای نگهداری. این را عوض می‌کنیم، بدون اینکه از اصل «ماژولار بودن» کوتاه بیایم:

> **تصمیم تعدیل‌شده:** یک ریپازیتوری واحد **Next.js Full-Stack** (App Router + Route Handlers یا Server Actions) با Prisma. منطق دامنه (Leitner, Notes/Cards, AI, Library) را در پوشه‌های مجزا با همان مرزبندی سند معماری می‌نویسیم (مثلاً `/lib/modules/leitner/service.ts`)، اما همه در یک پروسه اجرا می‌شوند.

**چرا این تصمیم درست است و به اصل معماری خیانت نمی‌کند:**
اگر منطق هر دامنه را در یک Service Class/فایل مستقل با ورودی/خروجی مشخص بنویسی (نه پخش در کامپوننت‌های React یا API Route ها)، روزی که تیم بزرگ شد و واقعاً نیاز به جداسازی Backend پیدا کردی، فقط این فایل‌های Service را به یک پروژه NestJS جدید **کپی می‌کنی** — منطق از قبل مستقل نوشته شده، فقط لایه انتقال (Controller به‌جای Route Handler) عوض می‌شود. این دقیقاً معنی «آماده مقیاس‌پذیری بدون هزینه امروز» است.

| لایه | تصمیم برای تک‌نفره | جایگزین آینده (وقتی تیم شدی) |
|---|---|---|
| Framework | Next.js 14+ (یک ریپو) | جداسازی Backend به NestJS |
| دیتابیس | PostgreSQL روی **Neon** یا **Supabase** (رایگان تا حد مشخص، بدون نیاز به مدیریت سرور) | همان، با Read Replica |
| ORM | Prisma (بدون تغییر) | بدون تغییر |
| Auth | **Clerk** یا **Supabase Auth** (نه دستی) — چند ساعت به‌جای چند هفته | همان یا NextAuth دستی |
| صف/Async | ابتدا **بدون BullMQ** — کارهای async ساده (مثل تولید AI تکی) را synchronous با Loading State بزن. وقتی حالت Bulk لازم شد (فاز ۷)، آن‌وقت Redis+BullMQ اضافه کن | BullMQ کامل |
| Hosting | **Vercel** (فرانت+API) — صفر تا هزینه پایین | Vercel + سرویس جدا برای Backend سنگین |
| فایل/رسانه | **Vercel Blob** یا **Cloudflare R2** (ارزان‌تر از S3) | S3 + CDN کامل |
| AI | مستقیم Anthropic API از Route Handler، بدون صف تا حالت Bulk لازم شود | صف اختصاصی |

این جدول یعنی: **هیچ تصمیم معماری اصلی سند قبلی دور ریخته نشد**، فقط زمان پیاده‌سازی هرکدام به تعویق افتاد تا واقعاً لازم شود (YAGNI — You Aren't Gonna Need It Yet).

## ۱. اصول طلایی توسعه‌پذیری (این‌ها را قبل از خط اول کد بخوان)

چون تیمی نداری که کدت را Review کند یا در جلسه معماری باهات بحث کند، باید خودت این نقش را برای خودت بازی کنی. این ۷ قانون، جایگزین آن تیم غایب هستند:

### قانون ۱ — مرز ماژول را با پوشه، نه فقط با نیت، حفظ کن
هر دامنه (Leitner، Notes/Cards، AI، Library، Exams) پوشه‌ی خودش را دارد و **هرگز مستقیم از دیتابیس ماژول دیگر کوئری نمی‌زند** — فقط از طریق تابع Service آن ماژول. حتی اگر امروز فقط تو کد می‌نویسی و «همه‌چیز را یادت هست»، شش ماه دیگر یادت نمی‌ماند. این قانون خودش را نجات می‌دهد.

### قانون ۲ — یک فایل `DECISIONS.md` نگه دار (ADR ساده)
هر بار تصمیم مهمی گرفتی («چرا Note/Card به‌جای مدل ساده»، «چرا فلان کتابخانه را انتخاب کردم و نه آن یکی»)، ۳-۴ خط در این فایل بنویس: تاریخ، تصمیم، دلیل. وقتی ۸ ماه دیگر به کدی برخوردی که منطقش یادت نیست، این فایل نجاتت می‌دهد.

### قانون ۳ — Feature Flag از همان روز اول
حتی برای تک‌نفره، یک جدول ساده `feature_flags` (یا فایل config) بساز. هر فیچر نیمه‌کاره پشت یک flag باشد. این یعنی می‌توانی کد ناقص را merge کنی بدون اینکه کاربر واقعی ببیندش، و بدون بحث و دعوا با شاخه‌های Git طولانی‌مدت (Long-lived Branch) که همیشه دردسر می‌شوند.

### قانون ۴ — API را از اول Versioned کن (`/api/v1/...`)
حتی اگر امروز فقط یک کلاینت (خودت) داری. این عادت باعث می‌شود وقتی اپ موبایل یا کلاینت دوم اضافه شد، مجبور نباشی همه‌چیز را بازنویسی کنی.

### قانون ۵ — روی «منطق حساس» تست بنویس، نه روی همه‌چیز
به‌عنوان تک‌نفره وقت کافی برای ۱۰۰٪ Test Coverage نداری و نیازی هم نیست. اما **الگوریتم لایتنر** (بخش ۵ سند فنی) باید تست واحد (Unit Test) داشته باشد، چون یک باگ ساده در این منطق (مثلاً همیشه به جعبه ۱ برگرداندن) کل تجربه یادگیری هزاران کاربر را خراب می‌کند و ممکن است هفته‌ها متوجه نشوی.

### قانون ۶ — Migration فقط از طریق Prisma، هرگز دستی
هیچ‌وقت مستقیم در دیتابیس (حتی در Development) جدول را دستی عوض نکن. همیشه `prisma migrate dev`. این عادت، سرمنشأ ۹۰٪ باگ‌های عجیب «چرا لوکال کار می‌کند ولی Production نه» را از بین می‌برد.

### قانون ۷ — طراحی «Note Type به‌عنوان پلاگین» را جدی بگیر
سند فنی v2.0 مدل Note/Card/Template را طوری طراحی کرد که افزودن یک نوع محتوای جدید (مثلاً بعداً «کارت گرامر» یا «کارت تلفظ IPA») نیازی به تغییر جدول دیتابیس نداشته باشد — فقط یک ردیف جدید در `note_types` با `field_schema` جدید. **این دقیقاً همان معنای واقعی «قابلیت اضافه کردن ماژول جدید» است که خواستی.** هر بار وسوسه شدی یک فیچر محتوایی جدید اضافه کنی، اول بپرس: «آیا این یک Note Type جدید است یا واقعاً یک ماژول کاملاً جدید؟» اکثر اوقات جواب اول است و کارت خیلی سریع‌تر از آن‌چه فکر می‌کنی حل می‌شود.

## ۲. جعبه‌ابزار مدیریت تک‌نفره

| **AI Pair-Programming** 🔑 | **Claude Code** (یا ابزار مشابه در ویرایشگر) | برای تک‌نفره این مهم‌ترین ضریب‌ضرب سرعت است — می‌تواند کارهایی مثل نوشتن CRUD تکراری، تست واحد، مهاجرت Prisma را با نظارت تو انجام دهد تا وقتت صرف تصمیمات معماری/محصول شود، نه تایپ تکراری |

| زمان‌بندی | **Toggl Track** (رایگان) — فقط برای اینکه بفهمی واقعاً کجای هفته وقتت رفته | تک‌نفره‌ها معمولاً تخمین زمان‌شان اشتباه است؛ داده واقعی کمک می‌کند |
| بازخورد کاربر | فرم ساده **Tally.so** یا Google Form بعد از هر مرحله انتشار | |
| مانیتورینگ خطا | **Sentry (پلن رایگان)** از همان MVP اول | چون تک‌نفره‌ای، نمی‌توانی منتظر بمانی کاربر با ایمیل بگوید «سایت خراب است»؛ باید خودت زودتر بفهمی |

## ۴. روتین روزانه و هفتگی پیشنهادی

چون تک‌نفره‌ای، اگر روتین نداشته باشی، وقتت بین «همه‌کاری کمی» تلف می‌شود. یک ساختار پیشنهادی:

### روتین روزانه (روزهای کاری)
| بازه | فعالیت |
|---|---|
| ۲-۳ ساعت اول روز (بهترین انرژی ذهنی) | **Deep Work** — فقط کدنویسی/معماری، بدون شبکه اجتماعی، بدون پاسخ به پیام. این بازه مقدس است. |
| میان‌روز | ادامه کدنویسی یا رفع باگ‌های سبک‌تر |
| بعدازظهر | پاسخ به کاربران، محتوا (شبکه اجتماعی/بلاگ برای بازاریابی)، بررسی Analytics |
| پایان روز (۱۵ دقیقه) | آپدیت Linear: امروز چه کاری تمام شد، فردا از کجا شروع می‌شود |

### روتین هفتگی
- **دوشنبه صبح**: مرور Backlog، انتخاب تسک‌های هفته از روی نقشه راه بخش ۳
- **جمعه (یا آخر هفته کاری)**: بازبینی: آیا هدف هفته محقق شد؟ اگر نه، چرا؟ (این عادت از تخمین‌های اشتباه پیوسته جلوگیری می‌کند)
- **یک روز کامل در ماه**: فقط روی بازخورد کاربر و متریک‌ها تمرکز کن، نه کد جدید — این روز جلوی «ساختن در خلأ» را می‌گیرد

### قانون طلایی ضد Burnout تک‌نفره‌ها
هر ۶ هفته کاری (تقریباً معادل ۱-۲ فاز از نقشه راه بالا)، **حداقل ۲-۳ روز کامل استراحت واقعی** بگذار (نه فقط قطع لپ‌تاپ، بلکه ذهنی هم قطع). پروژه تک‌نفره‌ای که با فرسودگی از پا می‌افتد، خیلی بدتر از پروژه‌ای است که یک هفته دیرتر لانچ شود.

## ۵. الگوی «افزودن ماژول جدید» — قانون ثابت برای هر فیچر آینده

این بخش مستقیماً به دغدغه اصلی‌ات (توسعه‌پذیری) پاسخ می‌دهد. **از همین امروز، هر بار خواستی چیز جدیدی اضافه کنی، این چک‌لیست ثابت را دنبال کن** — همین چک‌لیست، معماری منظم را حفظ می‌کند حتی وقتی هیچ تیمی برای نگه‌داشتنت نیست:

```
□ ۱. آیا این واقعاً یک ماژول جدید است، یا صرفاً یک Note Type جدید؟
      (طبق قانون ۷ بخش ۱ — اکثر ایده‌های محتوایی را می‌شود بدون کد جدید،
      فقط با یک ردیف در note_types حل کرد)

□ ۲. اگر واقعاً ماژول جدید است: یک پوشه مستقل بساز
      /lib/modules/{module-name}/
        ├── service.ts       (منطق دامنه)
        ├── types.ts         (تایپ‌ها)
        ├── schema.prisma-fragment.md   (جداول مرتبط، برای مرجع)
        └── service.test.ts  (حداقل تست روی منطق حساس)

□ ۳. یک Feature Flag برایش بساز قبل از اینکه به همه کاربران نشانش بدهی

□ ۴. Endpoint های جدید را زیر /api/v1/{module-name}/... بگذار

□ ۵. اگر جدول دیتابیس جدید لازم دارد:
      - آیا رابطه‌اش با جداول موجود (خصوصاً users, decks, words) درست تعریف شده؟
      - آیا exam_context را (اگر مرتبط است) رعایت کرده؟
      - Migration را بساز و نامش را معنادار بگذار

□ ۶. یک ورودی در DECISIONS.md بنویس: چرا این ماژول را الان اضافه کردی،
      چه بازخوردی باعثش شد

□ ۷. بعد از پیاده‌سازی: آیا این فیچر باعث شد کد ماژول‌های دیگر را
      "برای سازگاری" تغییر بدهی؟ اگر بله، این هشدار است که مرز ماژول‌ها
      دارد نشت می‌کند — قبل از ادامه، معماری را بازبینی کن
```

## ۶. نقاط تصمیم‌گیری حیاتی (Go / No-Go)

به‌عنوان تک‌نفره، بزرگ‌ترین ریسکت این است که بدون توقف، مدام کد بزنی. این چک‌پوینت‌ها را جدی بگیر:

### چک‌پوینت ۱ — بعد از فاز ۳ (Alpha)
**سؤال:** آیا حداقل ۳۰٪ کاربران Alpha، بعد از یک هفته هنوز برمی‌گردند مرور کنند؟
- ✅ اگر بله → ادامه به فاز ۴
- ❌ اگر نه → قبل از افزودن فیچر جدید، بفهم چرا. شاید مشکل از UX مرور است، نه کمبود فیچر. **فیچر جدید اضافه‌کردن، مشکل Retention پایین را حل نمی‌کند.**

### چک‌پوینت ۲ — بعد از فاز ۵ (درآمد اولیه)
**سؤال:** آیا حتی چند نفر (even ۵-۱۰ کاربر) حاضرند پول بدهند؟
- ✅ اگر بله → می‌توانی با اطمینان بیشتری روی فازهای بزرگ (AI, آزمون) وقت بگذاری
- ❌ اگر نه → قبل از فاز AI پرهزینه، بفهم چرا. شاید قیمت‌گذاری غلط است، شاید ارزش پیشنهادی واضح نیست

### چک‌پوینت ۳ — قبل از فاز آزمون‌ها (فاز ۹)
این فاز گران‌ترین فاز کل نقشه راه است. **سؤال:** آیا داده/بازخورد کاربران واقعاً نشان می‌دهد آزمون اولویت اول است، یا فرض تو بوده؟ اگر مطمئن نیستی، این فاز را با یک نسخه بسیار کوچک (فقط ۵ آزمون Reading نمونه، دستی وارد شده، بدون موتور نمره‌دهی پیچیده) تست کن قبل از سرمایه‌گذاری کامل.

## ۷. مدیریت خودت (روان و انرژی، نه فقط کد)

- **Impostor Syndrome طبیعی است.** تک‌نفره بودن یعنی هر روز باید هم مهندس خوبی باشی هم طراح هم بازاریاب. لازم نیست در هر کدام «عالی» باشی — فقط باید در حد MVP «کافی» باشی. برای تک‌نفره‌ها، *Perfect is the enemy of shipped.*
- **از AI برای کارهای غیر-تصمیم‌گیری کمک بگیر، نه برای تصمیم‌گیری.** بگذار Claude Code کد تکراری، تست، مهاجرت بنویسد. اما تصمیم «آیا این فیچر ارزش ساختن دارد یا نه» را خودت بگیر، بر اساس بازخورد کاربر واقعی.
- **Outsource کن جایی که هزینه‌اش کمتر از وقتت است.** مثلاً طراحی لوگو یا کاور کتاب‌های Placeholder را با یک فریلنسر ارزان (Fiverr, پونیشا) بده، وقتت را برای منطق محصول نگه دار.
- **جشن گرفتن پیشرفت‌های کوچک را فراموش نکن.** بدون تیمی که برایت کف بزند وقتی یک فیچر جواب داد، خودت باید یادت باشد بایستی و به عقب نگاه کنی ببینی چقدر پیش رفته‌ای.

## ۸. بودجه تخمینی ماهانه (Bootstrap)

| مورد | هزینه تخمینی ماهانه (فاز MVP) | هزینه بعد از رشد |
|---|---|---|
| Hosting (Vercel) | رایگان تا ترافیک متوسط | ۲۰-۵۰ دلار |
| دیتابیس (Neon/Supabase) | رایگان تا حجم مشخص | ۲۵-۵۰ دلار |
| Auth (Clerk) | رایگان تا تعداد کاربر مشخص | ۲۵ دلار به بالا |
| Anthropic API (فاز AI) | بستگی به مصرف — با Rate Limit سخت‌گیرانه، ۱۰-۳۰ دلار قابل کنترل است | متغیر با تعداد کاربر Premium |
| دامنه | ~۱۰-۱۵ دلار **سالانه** | همان |
| Sentry | رایگان تا حد مشخص | ۲۶ دلار به بالا |
| Unsplash API | رایگان | رایگان (با اعتبار مناسب) |
| **جمع فاز MVP** | **عملاً نزدیک صفر تا ۲۰-۳۰ دلار** | |

نکته: این یعنی از نظر مالی، ریسک شروع این پروژه به‌تنهایی بسیار پایین است — بزرگ‌ترین سرمایه‌گذاری‌ات «وقت» است، نه پول. این خودش دلیل خوبی است که فازبندی و اجتناب از Scope Creep (بخش‌های ۳ و ۶) را جدی بگیری، چون تنها منبع محدودت زمان توست.

```
□ این هفته چقدر از نقشه راه بخش ۳ واقعاً پیش رفتم؟ (نه چقدر کد نوشتم — چقدر
```

## جمع‌بندی

تنها راه واقعی که یک نفر بتواند پروژه‌ای با این حجم پیچیدگی (که در سند فنی v2.0 دیدیم) را بسازد و **ذهنش هم منفجر نشود**، این سه اصل است:

1. **فازبندی سخت‌گیرانه** — هر بار فقط روی یک فاز، نه رویای کل معماری
2. **مرزهای ماژولار به‌عنوان جایگزین تیم Review** — چون کسی نیست کدت را چک کند، خودِ ساختار پوشه‌بندی و قوانین بخش ۱ و ۵ این نقش را بازی می‌کنند
3. **تصمیم‌گیری بر اساس داده واقعی کاربر، نه فرض** — چک‌پوینت‌های بخش ۶ را واقعاً رعایت کن، حتی وقتی وسوسه می‌شوی رد شوی و مستقیم بروی سراغ فیچر بعدی

با این نقشه راه، در نگاه واقع‌بینانه، رسیدن به یک محصول **قابل‌فروش با هسته لایتنر + AI** (پایان فاز ۶) در حدود **۳-۳.۵ ماه کاری تمام‌وقت** از صفر، دور از دسترس نیست — و مهم‌تر از سرعت، این است که معماری‌ای که ساختی، در ماه ۱۲ همان‌قدر تمیز و قابل‌توسعه باشد که در ماه ۱ بود.
